# 低输入开书向导（Guided Hatching v3）

开新书的选择链由总编辑内联执行；分卷总纲是唯一派发出去的产物——门 8 定盘后由创意编辑设计（每书一次）。目标不是让作者填写设定表，而是让作者沿一条短选择链完成
方向裁决，然后一次确认启动。机器负责推导、组装与校验；作者通常只需回复 `A`、`B`、`C`、
`换一组`、`D`（自定义）、`N`（允许为空时）或 `返回`。

## 一、交互契约

1. 作者可以零输入开始，也可以给一句点子；已明确的信息直接记录为 `author_supplied`，不再提问。
2. 每轮只展示一个决策轴和 2~3 个可比较方案。每项用短语写清结果、收益、代价、风险；
   相同前提只在题干交代一次，有充分依据时才标推荐项。
3. 固定操作：`A/B/C` 选择、`换一组` 重看当前门候选、`D` 自定义、`返回` 修改上一项；
   允许为空的基础门及补充门额外允许 `N`。
4. 不要求作者解释选择。系统在选择后静默完成该门内的派生字段，并进入下一门。
5. 不按超时自动选择，不把“推荐”当作作者确认，不一次倾倒所有方案。
6. 改动上游选择时，从受影响的最早下游门开始失效重算；已无冲突的选择保持不动。
7. 选择链全流程内联执行，严禁每个选择唤起子 agent；候选生成、字段组装、校验都在同一上下文
   完成。唯一例外是分卷总纲：门 8 定盘后派一次创意编辑 job 起草各卷总纲（契约见[全书分卷合同](extend-contract.md)），回填后交互审阅仍内联。

## 二、九个基础决策门与按需补充

十八项内部设计要素仍需完整。九个基础门覆盖常见的全书方向选择，细节字段由系统在门内推导，
无需作者逐项填写。若具体项目出现无法从已有选择推导、且会实质改变故事结构或写作合同的独立取舍，
可增加补充门；不预设总步数，也不为凑数提问。

| 基础顺序 | 决策门 | 作者选择什么 | 系统在门内补齐什么 |
|---|---|---|---|
| 1 | `reader_promise` | 题材承诺、目标读者、核心体验 | 题材标签、高概念、卖点、基调初稿 |
| 2 | `plot_architecture` | 故事靠什么持续推进 | 叙事动力、结构模式、长线问题是否需要 |
| 3 | `protagonist_engine` | 主角的行动逻辑 | 姓名、处境、表/深层欲望、压力、缺陷、技能、物质生活 |
| 4 | `core_relationships` | 核心关系结构或 `none` | 参与者、独立诉求、边界、变化节奏；不预设性别和恋爱形态 |
| 5 | `world_opposition` | 世界约束与主要压力形态 | 硬规则、资源秩序、对抗方利益、首卷压力、盟友边界 |
| 6 | `story_mechanism` | 特殊故事机制或 `none` | 原理、代价、限制、失效条件、应对策略 |
| 7 | `main_arc` | 全书任务与终局方向 | 四层全书事件脊柱；全卷职责、因果承接与通向终局的路径 |
| 8 | `scale` | 规模、视角结构、平台尺度 | 书名、字数、全卷预算；卷数预算定盘后派创意编辑设计各卷总纲（每卷至少500汉字），之后细化首卷及前3章、红线 |
| 9 | `voice_style` | 全书叙述文风（独立于题材、主题、人物性格和规模） | 所选 `voice_id` 写入本门决策与 manifest 顶层 `voice` |

补充门紧接所依赖的基础门，放在下一基础门之前；同一位置可有多个，按依赖关系先后询问。
例如某书的双时间线能否互相得知消息，会改变悬念与因果安排，且作者尚未决定时，
可在情节架构门后另问一门。若作者已经说清，直接记录 `author_supplied`，不重复提问。
补充门由系统说明提问理由，沿用单轴、候选对比、返回修改和最终确认规则。
选出的结果须落实到相应的正典、大纲或叙事设置字段，不能只留在决策记录里。

基础门 9 从 `voice list` 取当前可用文风 id，按作者想要的叙述质感一次展示 2～3 种，
不把六套同时堆给作者；作者可用 `D` 指定列表中未展示的 id。题材、主题或前八门的
基调不能代选文风，任何题材都可选任何可用文风。作者未表明文风偏好时，候选必须包含
默认推荐的 `shijing`；换组时继续包含它，其余位置优先展示尚未出现的可用 id，
已无足够新 id 组成 2～3 项时说明文风候选已用尽，保留当前组供选择，并提示 `D` 或 `返回`。
仍须作者明确选择。作者此前已明确指定文风时，记录为
`author_supplied`，无需重复提问。内置方向是：`shijing` 市井烟火（具体事务与人情）、
`cinematic` 电影镜头（可见行动与空间）、`baimiao` 平实白描（克制直叙）、
`mystery` 悬疑冷峻（线索与认知差）、`heroic` 热血群像（协作、冲突与代价）、
`lyrical` 细腻抒情（感官、关系与余韵）。文风是表达选择，不代替题材、人物性格或项目正典。

基础门 8 遇到视角结构或平台尺度需要作者单独取舍时，可分别拆出短卡；作者已明确给出时直接记录：

- **视角结构**（`narrative_pov`）：`单视角限知 / 双主角交替 / 多线群像` 三选一，可 `D` 自定义锚点
  说明；选交替或群像时必须同时声明切换粒度（按章或按卷）。默认推荐单视角限知——pack 的
  NOW/在场/连续性机制本就以主角为锚。声明后随 plan 落盘并渲染进每章 writing_brief 定位段，
  写手始终知道本章用谁的眼睛、切换只发生在哪种边界。
- **平台尺度**（`content_fence`）：`严审安全线 / 中等尺度 / 分区分层 / 自由尺度` 四档 + 自由文本
  补充（目标平台、具体禁项指向红线）。档位随包渲染成写手约束；具体禁项仍由红线承接，两处
  不重复列举。

基础门 3 内额外执行**反套路命名纪律**（`protagonist_engine` 的姓名项）。
AI 起的主角名高度趋同：潇洒姓（叶/林/萧/楚/顾/沈/陆/苏/秦）×玄乎单字
（辰/尘/轩/言/夜/寒/渊/冥/烬/煜/珩/枫/炎/离）几乎覆盖了模型产出的两字名——读者一眼批量脸。
主角与首批核心角色的候选名、最终名都必须过四条：

- **姓氏贴世界与阶层**：市井/乡土用常见姓与俗字（张/王/李/赵＋铁/根/栓/福/贵/有），
  世家门第才配行辈字与雅字；任何题材的姓池都别扎堆在"潇洒姓"；
- **俗字与双字名优先**：单字玄乎名是重灾区；双字名天然更"真人"（张铁柱/李有粮/王守田）；
- **称呼链一次想好**：全名→日常称呼→诨名/职衔（张铁→铁哥→老张/张铁匠），群像书的
  称呼链就是人物识别系统，叫得出口的名字才立得住；
- **口语测试**：名字放进一句街坊对白念三遍，念着像网文签名档就换。

`book hatch` 对"潇洒姓×玄乎单字"的两字主角名回 `name_warnings[].code=protagonist_name_cliche`
（advisory 只警不拦，作者坚持以作者为准）。

九个基础门保持 `1→2→3→4→5→6→7→8→9` 的相对顺序，补充门插在其所依赖的基础门之后。
所有选择都在同一编辑上下文中短交互完成，不按门数委派模型。
晚期复杂产物（幕纲、卷脊、起手章拍）只合成一份与前述选择一致的草案，不并行生成三套完整大纲；分卷总纲不在此列——它由门 8 后的一次创意编辑 job 设计，其余产物的合成纪律不因它改变。

`reader_promise` 若明确选择通用凡人修仙底盘，可把随包种子记为顶层
`"background": "xianxia-mortal"`；未选择则不写此字段。它只补充公开基础正典，不替作者决定人物、
主线或特殊机制，也不增加新的交互门。

## 三、候选与决策记录

作者看到的是短卡：一行问句，每个候选一行，末尾给 `换一组`、`D` 自定义、`返回`，
允许为空时再给 `N`。
候选行按“`A 标签｜结果：…；收益：…；代价：…；风险：…`”呈现，每栏只用一个能区分方案的短语。
**代价**是选择后确定要付出的东西，**风险**是可能发生的不利后果；不要把结果改写三遍填满四栏。
推荐理由至多一句，只有已有意图或约束足以支持时才给。此处是展示格式，不改变下列 manifest 字段。

作者回复 `换一组` 时，留在当前决策轴，沿用已确认的上游选择、原始点子和约束，并吸收作者
随这次请求补充的偏好，另给 2～3 个方向实质不同的候选；可连续换组，不得把旧方案换名、
改写收益或微调细节冒充新组。
每次重新从 `A` 起编号，旧组字母与方案的对应关系立即失效；后续 `A/B/C` 只指最新一组。
推荐项及理由须按新组重算。
换组本身不代表选择，不自动推进，也不改动已确认的上游决定。若已无法给出实质新组，
说明原因并保留当前组，让作者选择、`D` 自定义或 `返回`，不得循环重复近似方案。

每个 `wizard.decisions[]` 记录：

- `id`、互不重复的单一 `axis`、固定 `cardinality: one`；九个基础门保持相对顺序，
  补充门按依赖位置插入；
- `options`：展示过候选时，只记录最后展示并供作者裁决的一组 2~3 项，不保存已换掉的组；
  `author_supplied` 未展示候选时可为空；ID 按 `A/B[/C]` 排列，每项含
  `label/outcome/benefit/cost/risk`；标签与结果不得重复；
- `selected`、`source`、`summary`、`status`；
- `custom_allowed: true`；基础门只有 `core_relationships`、`story_mechanism` 的
  `none_allowed` 为 `true`；补充门须显式写布尔 `none_allowed`，确实可不设该要素时才设为 `true`；
- 推荐项可选；一旦给出 `recommended_id`，必须同时给 `recommendation_reason`。
- `voice_style` 决策另有 `voice_id`：候选项各有不同且可用的 `voice_id`；选中候选时本门
  `voice_id` 必须等于候选 id 对应的文风 id，并始终等于 manifest 顶层 `voice`。自定义或
  `author_supplied` 也要记录本门 `voice_id`；可用性按 `voice list` 对应的手册校验。
- 补充门的 `id` 采用 `extra_<slug>`（小写字母起，只含小写字母、数字、下划线），
  `after` 写它前面最近的基础门 id，`reason` 简述为何需要单独裁决；这两个字段由系统记录，
  无需作者填写。补充门与基础门使用相同的确认、候选和唯一性校验。

若作者已经完整给出该门内容，记录 `source: author_supplied`，允许不生成候选；这正是减少无效输入与 token 的
主要路径。`custom` 表示作者在看过候选后提供新方向；`default` 只能用于作者明确选择推荐项，不能由系统代按。

## 四、最终确认与启动

实际需要的决策完成、起手前三章章拍已拟好后，只展示一页短摘要，分为三块：

1. **已选方向**：读者承诺、主角引擎、关系结构、对抗、机制、主线、首卷、规模、文风，
   以及补充门的选择与明确的 `none` 项；每项只写结论，不重述候选权衡。
   另按卷一行列出创意编辑设计的总纲摘要（职责 → 承接 → 终局方向）；作者改某卷即回创意编辑重拟该卷，其余卷不动。
2. **关键派生假设**：只列系统从已选方向推导、且会影响故事因果或前三章执行的假设，
   如人物初始处境、世界硬规则、视角切换或首卷开局压力；不把推导冒充为作者原话，
   也不重复已选方向。作者可据此发现推导偏差。
3. **前三章预览**：每章各一句“**目标 → 冲突 → 后果**”。从已拟的 `step6_beats.chapters`
   提炼：`goal` 已给则沿用；未给时由章拍和上游选择归纳目标；冲突与后果从章拍、上游选择及
   已有的 `effects` 提炼，后果写可观察的局面变化或代价。若任一环节无法从草案提炼，先回到编拍
   修正，不能在确认页临时虚构情节。预览只帮助作者核对，不新增 manifest 字段。

作者看过此页后只做最后一次选择：

- `启动`：写入 `wizard.status: confirmed` 与 `final_confirmation: true`；
- `返回`：指出要改的门或前三章推导；回到该门后仍可 `换一组`，旧组选择随换组失效，
  作者重新选择后按依赖规则重算受影响内容并更新确认页。

未收到“启动”时不得写入最终确认状态或执行建库。收到后才设置确认状态，先只读校验，再落库：

`book hatch` 同时将已确认的方向保存为 `plan.narrative_contract`，版本为
`novel-ledger.narrative-contract.v1`。它保留读者承诺、主角欲望与限制、主线任务与终局条件、
作者完整红线、世界规则/机制，以及已经声明的核心关系和主题，不新增未声明的主题或关系要求。
该结构不依赖聊天历史，完整进入后续空上下文策划与独立剧情复核；不设输入或生成字符／字节上限，不截断红线。
建库前必须签齐 `volume_outline_contract.volumes`：每卷完整卷纲至少500个汉字，明确职责、承接、矛盾与人物线、终局方向和下一卷接口，预算合计覆盖全书。卷纲由创意编辑设计、总编辑核合同一致性、作者在启动确认页终审；宿主无法派发创意会话时，显式降级为总编辑内联执行创意职责并在决策记录注明，不得静默回退。详见[全书分卷合同](extend-contract.md)。
尚未声明人物弧里程碑时，计划验证会给出明确诊断；
可设计变化弧或坚持原则的恒定弧，不要求固定的成长次数。

```bash
python3 "$SKILL_ROOT/scripts/novel_ledger.py" book hatch \
  --manifest "$HATCH_MANIFEST_JSON" --check-only
python3 "$SKILL_ROOT/scripts/novel_ledger.py" book hatch \
  --project "$PROJECT" --manifest "$HATCH_MANIFEST_JSON"
```

`--check-only` 不创建项目。建库成功后，完整确认清单写入
`book/editorial/hatch-manifest.json`，用于复现和审计；同时生成意图、大纲、正典种子与前 3 章计划。
随后运行一次 `chapter next`，应直接进入第一章 `draft`。

## 五、唯一有效的 manifest 版本

开书入口只接受 `schema: "novel-ledger.hatch.v3"`，不兼容 v1/v2，也没有旧项目导入开关。核心门禁：

- 九个基础决策齐全，所有实际增加的补充门也已确认，且最终启动确认必须为真；
  已确认的旧版 v3 八门 `scale_voice` 清单仅按原样复验与落库，新开书应记录独立的文风门；
- `relationship_structure`、`story_mechanism`、`material_life`、`long_arc_question` 必须显式
  `present` 或 `none`；`none` 不得暗带内容；
- 主线必须有任务、驱动力、首卷切口、终局事实与 2~5 个因果阶段；
- `step4_outline.event_spine` 必须显式分成 `mainline/subplots/timelines/tension_curve` 四层；事件带
  全书唯一 ID，每条线路和时间线只保留 2–8 个幕级触点，不生成全书章级细纲；
- 全卷总纲须先按 [volume-outlines.v1](extend-contract.md) 签齐，每卷定制、至少500汉字；首卷蓝图须与预签首卷一致，后续扩纲只能逐卷细化；
- 控制面按写作字数带的 aim 签出 `chapter_words_target`（默认 3200）；首卷 `chapters_budget`
  等于 `ceil(word_budget / chapter_words_target)`，全书章数同理，禁止固定成 60 章；
  旧书沿用已签约章幅；
- 起手计划必须恰为第 1~3 章，每章默认 5 拍，拍点不可为空，`must` 必须是拍文本中的具体子串；
- 起手章的 `location`、`present`、`tags`、`goal` 与按需 `kb_refs` 会原样进入 plan 与章节工作包；
  重要线索或旧盟友若在前三章登场，须在章拍给出这些切片锚，并以 `effects.hooks` 登记实际埋种；
- 可选 `character_profiles` 从已选主角引擎、职业处境与核心关系派生主要在场者的表达基线，
  不新增作者决策门；无证据的字段留空。`knowledge_refs` 也可用于起手章的关键认知话题。
  人物声线、误信与知识边界见 [角色声线](craft/character-voice.md)；
- 开书自动签出覆盖起手三章的 `phase-opening`，分别引用第一幕的一项主线事件、至少一项支线事件、
  至少一项时间线事件与第一幕起伏曲线，并生成进入态、退出态、逐事件变化；三章引用的并集必须
  覆盖该阶段全部主／支线和时间线。起手章自动挂该阶段，四层缺一不可；
- 红线必须显式选择 `present` 或 `none`；所有字段都使用 v3 标准名，不接受旧别名。
